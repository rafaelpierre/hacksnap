# Issue #135 — enrichment coverage evaluation

Prepared 29 September 2026. **Decision: defer worker expansion.** Issue [#132](https://github.com/rafaelpierre/lighthouse-hacker-news/issues/132) and its prerequisite [#131](https://github.com/rafaelpierre/lighthouse-hacker-news/issues/131) are still open. There is no recorded post-release measure of readers reaching the end of the usable feed. This is an evaluation of the checked-out code and existing repository evidence, not a new production baseline.

## Current behavior and known evidence

- The worker selects the first **50** rows from `hacksnap_ranked_stories`, in rank order. It attempts each selected ID at most once per run, with at most 15 active jobs, then rereads the top 50 for replacements. The 50 limit includes cached summaries, missing retained content, fetch failures and inference failures. Existing summaries are still examined for discussion/sentiment refresh. Thus the worker does not guarantee 50 new briefs, and an unsummarized story below rank 50 cannot enter this run solely because earlier rows were cache hits. See [`config.py`](../../../hacksnap/pipeline/config.py), [`supabase.py`](../../../hacksnap/pipeline/supabase.py), and [`refresh.py`](../../../hacksnap/pipeline/refresh.py).
- The ranking view prefers stories added in the last 24 hours, then points and HN ID; it excludes recorded fetch failures for the current URL. `hacksnap_current_stories` is still a separate top-ten view. The homepage selects up to ten ranked stories that have a summary row with a nonblank `overall_takeaway`. A null `article_summary` can be a valid discussion-only brief. Count a *usable brief* by the homepage predicate, not by `article_summary IS NOT NULL`. See [ranking migration](../../../data/migrations/versions/0011_categories_add_story_categories.py) and [feed query](../../../hacksnap/web/lib/data.ts).
- A missing `hn_thread_contents` row returns `unavailable` before the summary lookup or inference. A same-URL article fetch failure is persisted and excluded by the ranked view; a corrected URL becomes eligible again. Model/validation/database failures are isolated per story and can be tried on a later run; there is no persisted inference retry count or backoff. Existing summaries use fingerprints to avoid unchanged discussion/sentiment inference. The run records result counts and timing; the Modal invocation can finish even when individual stories fail. See [`refresh.py`](../../../hacksnap/pipeline/refresh.py) and [worker telemetry](../../../hacksnap/README.md#workflow-concurrency-and-timing).
- The last repository write-up with a direct database inspection is [28 September's pending-summary investigation](../2026-09-28-pending-summaries.md). It observed 185 eligible ranked stories, 75 without summaries, 50 of those without retained source, and a then-top-ten with seven pending. That predates the current 50-story worker policy and is **historical context**, not today's counts or proof of scrolling exhaustion. Its live inference probes addressed truncation, not depth demand.

The current code has `story_view` and `reader_visit` events, but no event identifying a homepage open *beyond* the first ten or a reader-visible feed end. Issue #132 specifies that distinction and has not supplied a release evaluation. The analytics [baseline register](../../analytics/README.md#baseline-register--pending) also marks production access and measured results pending. Worker code and an open issue cannot establish production deployment state or user demand.

## Baseline to collect after #132 releases

Run [`baseline.sql`](baseline.sql) in a read-only transaction against the deployed schema at a fixed UTC snapshot. Save the query text, run time, release commit, migration version, result rows and access role. Repeat after each scheduled worker run for 14 complete days, including weekdays and weekends. The query separates eligible **source volume**, ready briefs, pending stories with retained source, and pending stories whose source has expired. A retained row guarantees non-null `full_raw_text_contents` under the schema, but does not guarantee parseable or useful source; inspect failures separately. Rank bands matter because a large all-time inventory may not make the first few feed pages usable. Save the per-story snapshot result outside the repository and compare each ID's ready state across snapshots. Count newly observed ready briefs by day from `not ready → ready` transitions, and separately count newly collected IDs first seen ready after the previous snapshot. Estimate collection-to-ready as an interval between the last observed pending time and first observed ready time, using `date_added` as the earliest possible start for a newly collected ID. Report already-ready stories at the first snapshot as left-censored, and missing snapshots or stories leaving eligibility as incomplete observations. Check that summary rows meet the homepage nonblank predicate and sample null-article-summary briefs as valid discussion-only content.

`generated_at` is **not** an immutable first-publication timestamp: [`save_summary`](../../../hacksnap/pipeline/supabase.py) resets it on an upsert. `updated_at` changes on other refreshes. Neither can recover historical daily new briefs or first-ready lag. The snapshot method gives bounded observation intervals and can miss a story that becomes ready and leaves eligibility between samples. If exact timestamps become necessary, add an immutable `first_ready_at` in a separately reviewed database change; do not infer it from the current columns. The 28 September historical counts below remain a separate one-time observation.

Match those snapshots with worker `refresh_completed`, `summary_job_completed`, `inference_timing` and token-usage spans for the same UTC windows. Report attempted, generated, unchanged, unavailable, fetch-skipped and failed counts; p50/p95 collection-to-ready delay, job wait, inference and whole-run time; and input/output/cached tokens by operation and model. Price the observed tokens using the **actual endpoint billing terms for that window**, recording the rate source and currency. Report cost per newly usable brief and total daily cost. The existing 40-minute Modal timeout and 15-job concurrency are ceilings, not observed latency or a cost estimate. Review failed story IDs privately to distinguish transient inference faults from lost retained source; do not export prompts or source text into the report.

For reader demand, #132's release must record actual opens of stories at positions 11+, visible/manual end-of-feed encounters, and load/error/expired-session outcomes. A fetched batch, mounted card, automatic request, or generic page view is not a deeper-story open. Record denominator as sessions reaching a point where another batch *could* be requested, plus sessions that actually reach the end; segment by device and visit cohort. Join only aggregate daily counts to the worker inventory; do not infer individual reader intent from server availability. Verify a normal return journey after several loaded batches before interpreting a low deeper-open count as disinterest. The first complete production window is a **first observed baseline**, not a pre/post improvement claim.

Interpret the four distinct questions in order:

1. **Availability:** Are there enough eligible ranked HN sources, particularly past rank 10, on the days readers run out? If not, enrichment capacity cannot create sources.
2. **Readiness:** How many have a usable brief at the time of a feed visit, and how long after collection did they become ready? A pending item with expired source is not recoverable by simply raising the run cap.
3. **Coverage:** Among eligible pending items with retained source, are many outside the current 50 attempts or repeatedly displaced by cached top-50 work? Compare rank-band counts and worker outcomes before attributing a short feed to selection capacity.
4. **Demand:** Do readers actually reach the available end and seek more, with reliable navigation? Without observed demand, additional model work has no demonstrated product benefit.

## Conditional experiment, not an approved change

Reopen only after a stable #132 release and two complete weeks of matched inventory, worker and reader data show repeated *reader-visible* exhaustion, while eligible pending stories with retained source exist just beyond the 50-story attempt window. Inspect at least several affected daily snapshots and report counts, denominators, p50/p95 delays and representative failure causes. If the shortage is source volume, failed fetches or inference reliability, address that cause under its own scope first. If the existing 50 already produces enough ready depth, defer again.

For the first capacity trial, keep the ranked top-50 priority lane and its current refresh semantics. Only after that lane completes successfully enough to leave a safe time margin, select at most **10 additional distinct** unsummarized stories from ranks **51–100**, ordered by `(rank, hn_id)`; require retained source and no current-URL fetch-failure exclusion. Never select an already usable summary simply to fill the feed. This is a proposed ceiling of **60 total story attempts and 10 extra initial-summary inference attempts per run**, at the existing maximum 15 active jobs, with **zero** extra attempts when less than eight minutes remain before the 40-minute function timeout. A story that fails in the extra lane consumes its attempt; do not refill it in the same run. Keep the extra lane behind the priority lane so its fetching, model calls and database work cannot delay top-50 publication. The selector should use a consistent ranked snapshot and deterministic ordering, then skip IDs already attempted by that run. Any implementation must address inference failures across runs with a bounded retry/backoff policy rather than repeatedly spending the extra budget on a permanently failing story. Source cleanup must not remove a selected pending story before its job completes.

Before enabling the trial, compute a currency budget from baseline tokens per new brief and the current endpoint price. Proposed **additional daily spend ceiling: 20% of the measured median daily inference spend in the baseline window**, alongside the 10-extra-attempt per-run ceiling (at most 160 additional attempts on the current 16-run daily schedule). Reserve each candidate's worst-case input and configured output-token cost *before* dispatch, across runs; reconcile against actual usage afterward. If a reservation would exceed the daily cap, skip it. A per-run count or after-the-fact token tally alone is not a spend bound because response tokens vary. Review existing priority p95 readiness and runtime, baseline summary quality samples (including no-article and sparse-discussion cases), and current failure/truncation rate. Roll out to a small fraction of scheduled runs or a short reversible canary, with lane-tagged logs and a comparison window over matching days. Proceed only if reader-visible ready depth and deeper opens improve without worse priority readiness, semantic quality, failure rate, or p95 runtime; set numerical thresholds from the measured baseline before rollout. Pause the extra lane on any daily cost-cap breach, repeated timeout, quality regression or priority-delay threshold breach. Rollback is the existing 50-story selector, leaving saved valid briefs intact.

Conditional code work requires deterministic selection, cap, cache-hit, missing-source, retry, failure, and timeout regression tests; `uv run --directory hacksnap pytest` and `uv run --directory hacksnap ruff check pipeline tests modal_app.py`; database query-plan review under production-like volume; and a separate authorized deployment. No worker or database behavior is changed by this evaluation.
